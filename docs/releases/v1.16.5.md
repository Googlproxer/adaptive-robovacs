# Adaptive RoboVacs v1.16.5

This release prevents a dashboard manual occurrence from issuing another room
clean while its current physical stage is still running. The reported sequence
was a normal Roborock mid-clean dustbin-empty visit followed by a native resume;
the persisted manual override incorrectly remained eligible for integration
dispatch while the same occurrence stage was already marked running.

- Only a durable `pending` occurrence stage may form or pass a dispatch. A
  `running` stage remains owned by active-job observation and recovery, even if
  the primary vacuum entity temporarily reports `docked`.
- A second guard at the final application dispatch boundary checks the current
  occurrence identity, stage index, pending status, and absence of another
  active job before the adapter can send a command.
- Manual physical readiness now requires a docked primary state, a dispatchable
  same-device detailed status, and no Adaptive RoboVacs active job. Roborock
  `emptying_the_bin`, mop washing, returning, cleaning, and unavailable states
  therefore cannot satisfy the manual gate.
- A fresh explicit dashboard button press remains immediate user intent after
  those physical checks. Persisted manual continuations considered by automatic
  evaluation do not inherit that immediacy.
- Scheduled work and persisted manual continuations now require three
  uninterrupted minutes of physical dock readiness. Cleaning, returning,
  emptying, washing, unavailability, or an active job resets the interval. The
  interval is transient, so a Home Assistant restart conservatively starts it
  again.
- The existing Roborock lifecycle remains authoritative: a nonterminal dock
  visit keeps the active job, and a native transition back to cleaning resumes
  that same job without any Adaptive RoboVacs dispatch.

## Compatibility

Public entity IDs, stable unique IDs, dashboard resources, Store schema 18,
room cadence, manual override scope, and vendor mappings are unchanged. This is
an integration runtime change, so exact-tag HACS installation and a Home
Assistant restart are required.

The running stable environment is Home Assistant Core 2026.9.2. Its update
entity reported no newer stable Core release on 16 September 2026. The pinned
acceptance environment remains Home Assistant 2026.9.2,
pytest-homeassistant-custom-component 0.13.365, pytest 9.1.1, pytest-cov 7.1.0,
Ruff 0.16.7, and mypy 2.3.1. PyPI reported those pins current, and the official
`actions/checkout@v7` and `actions/setup-python@v7` majors remain current.

## Validation

Focused coverage reproduces a running manual stage during a nonterminal dock
visit, verifies that repeated evaluations send no dispatch, permits the native
cleaning resume to retain the active job, and checks the final terminal
completion path. Additional boundary tests cover detailed dock servicing,
active-job rejection, the 2:59/3:00 readiness boundary, readiness reset,
restart-conservative state, fresh explicit manual intent, stale occurrence
identity, and final dispatch refusal.

Local validation against Python 3.14.7 and Home Assistant 2026.9.2 passed 479
unittest cases and 479 pytest cases with 95.90% branch-aware coverage. The 30
dashboard tests, Ruff formatting/lint, strict mypy, root and recursive Python
compilation, release contracts, JSON parsing, and shipped dashboard/icon parity
also passed. GitHub Actions must reproduce the release validation before live
deployment.

## Deployment

Install exact tag `v1.16.5` through HACS and validate Home Assistant
configuration before restart. An active-clean restart is permitted only with
explicit user authorization; otherwise wait for positive docked, non-servicing
states. After restart, wait for the integration to report loaded and for startup
settling to finish, verify HACS reports `v1.16.5`, and confirm active robot state
was recovered from observation. Do not dispatch a clean solely for verification.
