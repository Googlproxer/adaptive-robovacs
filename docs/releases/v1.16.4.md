# Adaptive RoboVacs v1.16.4

**Recheck and resume** is now a global, explicit, non-dispatching recovery
action. It inventories robot holds, robot dispatch faults, room-scoped faults,
room recoveries, and retired-map holds, then rechecks each independently.

- The action now finds durable `RobotHold` records even when no matching
  `SchedulerFault` remains. This fixes an orphaned error hold that previously
  left a docked, error-free vacuum blocked indefinitely.
- A hold can clear when the vacuum has physically resumed cleaning, or when it
  has remained docked for the readiness-confirmation interval, its normalized
  error telemetry is clear, its detailed vendor status is terminally ready, and
  startup state settling has finished.
- A docked tracked attempt is cancelled in scheduler state without completion
  credit. Its scheduler stage returns to pending; an attached recovery episode
  is removed so normal scheduling can form a clean retry.
- A physically resumed tracked clean keeps its activity and timing continuity.
  Recheck never pauses, starts, returns, or otherwise commands a vacuum.
- Partial success is supported: safe holds clear while unsafe or unavailable
  targets remain durable. Every remaining non-map robot hold now owns a
  persistent scoped Home Assistant Repair containing only normalized reason and
  state text. Existing room and mapping Repairs remain independent.
- A successful global reset publishes a dry-run schedule preview. Occupancy,
  adjacency, desired windows, battery, robot readiness, Party Mode, and
  observe-only mode remain ordinary future-dispatch gates and are never
  bypassed by recovery.
- Robot Status now projects a hold without a dispatch fault as `Scheduler held`
  with `repair_active: true`. The dashboard's confirmation describes the full
  global reset and its no-test-clean behavior.

## Compatibility

Public entity IDs, stable unique IDs, Store schema 18, room cadence, scheduling
priority, and dispatch safety rules are unchanged. The served dashboard changed,
so HACS installation and a Home Assistant restart are required. Existing
`robot_error_recovery` Repair IDs are retained and now use the generalized
hold-recheck flow.

The running stable environment is Home Assistant Core 2026.9.2 on Home
Assistant OS 18.2. The pinned acceptance environment remains Home Assistant
2026.9.2, pytest-homeassistant-custom-component 0.13.365, pytest 9.1.1,
pytest-cov 7.1.0, Ruff 0.16.7, and mypy 2.3.1. Those package releases and the
official `actions/checkout@v7` and `actions/setup-python@v7` majors were current
when this release was prepared.

## Validation

Local validation against Python 3.14.7 and Home Assistant 2026.9.2 passed 475
unittest cases and 475 pytest cases with 95.97% branch-aware coverage. The 30
dashboard tests, Ruff format/lint, strict mypy, root and recursive Python
compilation, release contracts, JSON parsing, and shipped dashboard/icon parity
also passed. GitHub Actions must reproduce the validation before deployment.

Focused coverage includes the docked orphan-hold regression, vendor error and
terminal-status refusal, startup and stable-dock timing, physical-resume
continuity, active-stage reset without clean credit, idempotence, partial
multi-robot success, scoped Repair lifecycle, and no-dispatch command routing.

## Deployment

Install exact tag `v1.16.4` through HACS after GitHub Actions succeeds. Confirm
both vacuums are positively observed docked and not servicing before restarting
Home Assistant. Wait for startup state settling, verify the integration is
loaded and HACS reports `v1.16.4`, then press **Recheck and resume**. For the
reported Rob incident, the stable `docked` primary state, `charging` detailed
state, and clear error sensor should release the orphaned hold and leave Rob
eligible for normal scheduling. Do not dispatch a clean solely for verification.
