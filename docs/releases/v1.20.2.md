# Adaptive RoboVacs v1.20.2

Released 5 November 2026.

## Changes

- Process increasing native cleaning timers through a lightweight path only for
  a confirmed, currently observed cleaning job without a hold, fault, or room
  recovery. Persist its progress evidence and latest observation on every update.
  Suppress full planning/publication only for increments within 30 seconds of
  the latest evaluation; the next increment after that window evaluates fully.
  When both robots are cleaning, checkpoint both observations together. A hold,
  fault, recovery, or uncertain active job anywhere keeps full reconciliation.
- Continue evaluating occupancy, robot state, battery, capability changes,
  unavailable/reset timers, pending starts, and recovery conditions immediately.
  Existing scheduled deadlines continue to run independently of timer traffic.
- Serialize durable state once for comparison, validate actual writes once at
  the Store boundary, and skip validation when durable state is unchanged.
  Update the stored fingerprint only after a successful write. Forced saves and
  dispatch checkpoints retain their existing durability and ordering.
- Cache identical room/time/duration forecasts only during synchronous planning.
  Discard the cache before persistence, notifications, profile preparation, and
  dispatch awaits. Existing fresh occupancy and robot-state dispatch gates remain.
- Skip a Home Assistant entity write when that entity's exposed state, attributes,
  metadata, capabilities, and availability are unchanged, even when its broader
  room or robot scope changed.
- Add a synthetic active-clean and sequential native timer benchmark. It uses
  an isolated Home Assistant, memory Store, and a guard against all service calls.

## Compatibility and migration

No Store schema migration, entity-ID changes, dashboard edits, or configuration
changes are required. All existing dashboard attributes are retained. Progress
checkpoints survive restart, and a restarted job remains excluded from duration
and vacancy training where the existing recovery rules require it. Party Mode,
observe-only mode, and robot observations retain their authority over dispatch.

The live read-only version check found Core 2026.10.4. On 5 November the official
[stable feed](https://version.home-assistant.io/stable.json) and
[PyPI](https://pypi.org/project/homeassistant/) offered 2026.11.0, while the live
update entity still reported 2026.10.4 as latest. No live upgrade is included.
The latest [test plugin](https://pypi.org/project/pytest-homeassistant-custom-component/)
0.13.375 still requires Core 2026.10.4 exactly, so the compatible test dependency
set remains pinned to that version rather than overriding its Core dependency.
Local validation and before/after benchmarks use Python 3.14.9, matching CI.
Other pinned Python tools remain current. Official checkout v7.0.1,
setup-python v7.1.0, and upload-artifact v7.0.2 remain compatible with the existing
major-v7 action pins and read-only workflow permissions.

The compatible Playwright patch update is pinned to 1.64.1 in both the Python
benchmark requirements and JavaScript browser-test package/lockfile.

## Validation and deployment

See [performance documentation](../performance.md) for the reproducible workloads,
measurement boundaries, and local comparison results. Validation covers the full
Python suite and coverage gate, unittest, formatting/lint, strict typing,
compilation, dashboard tests, browser regressions, and shipped-file parity.

Final local validation passed 645 pytest cases with 95.37% combined statement/
branch coverage, the same 645 unittest cases, Ruff formatting/lint, strict mypy
across 65 production modules, and both required compilation checks. All 44
dashboard tests and 10 browser regressions passed; two existing browser cases
were skipped. Dashboard and icon copies remain byte identical. Windows pytest
used `-p no:homeassistant` for the plugin's Linux-only `fcntl` import; the suite's
explicit isolated Home Assistant tests still ran.

The 30-sample active-clean comparison reduced median evaluation time from
127.5 ms to 63.9 ms (49.9%), and a batch of 16 sequential timer updates from
2,289.1 ms to 567.1 ms (75.2%). All 16 updates retained durable Store writes.
The timer batch still exceeds its advisory 500 ms p95 budget. These measurements
exclude disk, Recorder, native devices, and clients; they do not establish the
percentage reduction in live VM CPU usage.
