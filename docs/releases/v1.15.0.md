# Adaptive RoboVacs v1.15.0

## Changes

- Keep each room's existing Next clean entity and unique ID, and expose a
  timezone-aware timestamp instead of countdown/status text. Its attributes
  contain only integration discovery metadata and room/floor identity.
- Add room Status sensors with activity, blocking reasons, diagnostics, enabled
  state, floor-based robot membership, and per-robot conditional preview reasons.
  Future work uses Scheduled; active jobs, recovery, holds, and robot readiness
  remain separate from the conditional timestamp.
- Calculate eligibility from the effective cadence, persisted initial baseline,
  recognised room deferral, and pending occurrence. Windows include inherited
  bounds, bypasses, overnight periods, and DST gaps/folds. Reached timestamps stay
  stable until a real scheduling change or window closing.
- Render Status, Next clean, Last clean, duration, occupancy, and controls in the
  room dashboard. Browser countdowns retain existing rounding and wording, show
  Due now when reached, and suspend timers while hidden or disconnected.
- Supply an Auto-entities template using existing Bubble Card rows for robot
  popups. It joins entities by entry and room identity, filters enabled rooms by
  membership, orders conditional times before status rows, and refreshes local
  day labels without writing entities. Wrapped rows fit narrow displays.

This implements the combined next-clean and Kiosk work for issue #7 on top of
the completed v1.14.1 application-package refactor. No new Kiosk card or fork is
introduced, and no live dashboard identifiers are stored in the repository.

## Migration

The `room_schedule` role and `room_{area_id}_next_clean` unique-key suffix are
unchanged. Next clean changes state type from text to a timestamp or unknown.
Existing recorder history is retained, including historical textual values;
history is neither converted nor deleted. Timestamp-based consumers should
handle old text and missing/unavailable values when reading older history.

Diagnostics and activity consumers must move to `room_status`, whose new unique
key suffix is `room_{area_id}_status`. This includes duration, occupancy reasons,
candidate/robot eligibility, occurrence, recovery, and failure attributes. The
integration's dashboard performs that migration automatically and retains a
fallback for the previous sensor layout. Last clean's behavior is unchanged.

The immutable presentation clock changes no scheduler evaluation frequency,
commands, durable cadence, jobs, or Store data. Store schema **17** is unchanged.
Existing occupancy, Party Mode, observe-only, recovery, and dispatch safeguards
continue to apply. A Next clean timestamp is conditional eligibility, not a
guaranteed start, forecast of when a blocker clears, or simulated queue position.

See [dashboard setup and the template contract](../dashboard.md).

## Validation

- 434 Python tests and 560 subtests passed, with 96.26% coverage (95% required).
- 28 dashboard tests passed, including countdown boundaries, hidden/disconnected
  cleanup, entity-details actions, Status duration consumers, and legacy fallback.
- HA runtime tests verified no `state_changed` event from repeated Next clean
  writes when only time/diagnostics advance, and no entity writes from Kiosk
  day-label refreshes. Template subscriptions track time explicitly.
- Kiosk tests cover entry/room joins, shared membership, chronological/name
  ordering, disabled rooms, blockers, missing data, and empty schedules.
- Ruff formatting/lint, strict mypy, unittest compatibility, root/recursive
  compilation, dashboard byte parity, and brand icon parity passed.
- Isolated browser checks used the official Bubble Card 3.3.0 with synthetic data
  at 320 px and 680 px. Conditional times, long names, and recovery reasons render
  without clipping. Live template evaluation via MCP also succeeded.
- MCP consumer searches found no additional stored automation, script, scene,
  helper, or dashboard references to the old entity names/diagnostic contract.

## Deployment and activation

Publish the annotated `v1.15.0` tag and full GitHub Release, verify CI, install
that exact HACS tag, and validate Home Assistant configuration. Apply targeted
Kiosk schedule-section updates using a fresh dashboard hash, and cache-bust the
existing served frontend resource with `?v=1.15.0`.

**Do not restart Home Assistant or reload the integration for this deployment.**
The user will restart manually. HACS's installed version confirms downloaded
files, not activation of new Python modules. Until that restart, the new Kiosk
sections report schedule data unavailable because room Status entities are not
yet loaded; the Adaptive dashboard uses its legacy fallback.

After the manual restart, verify the integration is loaded, Status entities and
timestamp states are present, both robot popups populate, and the Adaptive room
cards display the new layout. Keep robot observations and safety holds intact.
