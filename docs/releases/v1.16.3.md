# Adaptive RoboVacs v1.16.3

Due rooms now compete for available robot capacity by the longest time since a
completed full-room clean. A room with no recorded completion ranks first;
otherwise, the oldest aggregate completion wins before the existing due-time,
forecast-confidence, and stable-discovery tie-breakers.

- The priority source is persisted `RoomHistory.cleaning_completed_at`, matching
  the room's Last cleaned entity rather than its latest vacuum or mop stage.
- The rule applies to fresh candidates and persisted multi-stage occurrences.
  A pending follow-up stage therefore retains the room's previous full-clean age
  until the complete configured program finishes.
- An older ineligible room does not reserve a robot or prevent a younger eligible
  room from being assigned. Independent robots can still start separate work in
  the same evaluation.
- Cadence and due times still determine whether a room is eligible. Occupancy,
  adjacency, desired windows, Party Mode, observe-only mode, readiness, faults,
  Repairs, and final dispatch revalidation are unchanged.
- Explicit dashboard manual actions retain their immediate path and all existing
  safety checks.

## Compatibility

Public entity IDs, stable unique IDs, entity attributes, next-clean timestamps,
and Store schema 18 are unchanged. No migration, setting, dashboard JavaScript,
or resource cache-bust is required.

The pinned acceptance environment remains Home Assistant 2026.9.2,
pytest-homeassistant-custom-component 0.13.365, pytest 9.1.1, pytest-cov 7.1.0,
Ruff 0.16.7, and mypy 2.3.1. These were rechecked against the running stable Core
version and current package releases; the official checkout/setup action majors
also remain current.

## Validation

Local validation against Python 3.14.7 and Home Assistant 2026.9.2 passed 468
unittest cases and 468 pytest cases with 96.29% branch-aware coverage. The 30
dashboard tests, Ruff format/lint, strict mypy, root and recursive
Python compilation, release contracts, and shipped dashboard/icon parity also
passed. GitHub Actions must reproduce the validation before deployment.

Focused coverage includes the observed inverse ordering where Kitchen is due
earlier but Rumpus has the older full-room completion, never-cleaned priority,
unchanged tie-breakers, blocked-oldest fallback, and aggregate history carried
through a persisted pending stage.

## Deployment

Install the exact `v1.16.3` HACS release and validate Home Assistant
configuration. Restart only after both vacuums are positively observed neither
cleaning nor servicing; an unavailable state is not sufficient evidence. After
restart, verify the integration is loaded, HACS reports `v1.16.3`, existing
faults remain untouched, and the scheduler preview reflects the new ordering.
Do not clear a hold or dispatch a clean solely for verification.
