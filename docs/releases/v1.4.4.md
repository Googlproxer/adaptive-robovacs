# Adaptive RoboVacs v1.4.4

Version 1.4.4 hardens scheduler recovery, durable robot identity, forecasting,
and config-entry lifecycle behavior following a full-project review.

## Fixes

- Store schema v6 keys robot settings, active-job checkpoints, holds, and new
  duration samples by stable entity-registry identity. The migration retains
  the original vacuum entity-ID fragment for existing Adaptive RoboVacs unique
  IDs, so a vacuum rename does not duplicate controls or lose history.
- A held job found docked after an offline interval now reaches its documented
  expected-duration classification instead of remaining held indefinitely.
- Final vacancy forecasting uses the assigned robot's learned duration and is
  repeated immediately before preparation and physical dispatch.
- Config-entry unload gates new work before platform teardown and drains
  config-entry-owned evaluator tasks. Entry removal no longer reads unloaded
  runtime data and removes every owned Repair and Store payload.
- Current-schema Store values now validate global daily windows, forecast
  confidence, cadence, expected duration, and minimum battery bounds. Invalid
  data activates storage safe mode rather than reaching runtime scheduling.
- Supported robot profile fields expose an explicit **Not configured** value;
  stale saved vendor values remain visible instead of being replaced by the
  first advertised option.
- Mop intensity and mop mode discovery prefer same-device registry translation
  metadata, with option matching retained as a fallback.

## Migration

The schema-v6 migration runs after registry discovery so legacy vacuum entity
IDs can be resolved to stable registry IDs. Exact current IDs, retained entity
aliases, occurrence assignments, and an unambiguous one-robot legacy mapping
are migrated automatically. Ambiguous legacy keys are preserved but left
unattached, preventing settings from being assigned to the wrong vacuum.

No public Adaptive RoboVacs entity ID or unique ID is intentionally changed.
The current vacuum entity ID remains transient and is used only for live state
reads and service calls.

## Validation and deployment

Validation completed with all 117 Python unit tests, compilation of every
top-level integration Python module, all 11 dashboard Node tests, and byte
parity checks for both dashboard copies and both icon files. Install the exact
`v1.4.4` tag through HACS and restart Home Assistant only after confirming both
vacuums are not cleaning.
After restart, verify the integration is loaded, robot settings survived the
migration, renamed vacuums retain their Adaptive RoboVacs entities, and no
post-unload dispatch is possible.
