# Adaptive RoboVacs v1.16.7

This release fixes repeated Home Assistant Repair notifications for a robot
error that is already owned by an active room recovery. In the reported case,
Rob's main-brush error interrupted a room job and correctly held the scheduler.
The room recovery created its scoped Repair and removed the older generic
robot-hold Repair, but each subsequent robot state evaluation recreated that
generic Repair. The room recovery then removed it again, producing a roughly
30-second notification loop while the underlying error and hold were stable.

- A robot-error hold is omitted from the generic Repair projection only when a
  non-detached room recovery matches the active job's robot, room, occurrence,
  and stage.
- The room recovery remains the single Repair owner for that interruption.
- Detached recoveries, mismatched jobs, orphaned holds, and non-room hold
  reasons continue to produce the generic robot-hold Repair.
- Repair reconciliation does not clear or rewrite the durable hold, job, or
  recovery state and sends no robot command.

change, so an exact-tag HACS installation and Home Assistant restart are
required.

## Validation

Focused coverage reproduces the original ownership conflict, runs repeated
hold-Repair reconciliation, and verifies that the room Repair remains the only
visible representation while the durable hold and interrupted job are left
unchanged. Additional coverage proves that detached, mismatched, and
independent holds still retain their generic Repair.

Local validation against Python 3.14.7 and Home Assistant 2026.9.2 passed 484
unittest cases and 484 pytest cases with 95.84% branch-aware coverage. The 30
dashboard tests, Ruff 0.16.8 formatting/lint, strict mypy, root and recursive
Python compilation, release contracts, JSON parsing, and shipped dashboard/icon
parity also passed. GitHub Actions must reproduce the release validation before
live deployment.

## Deployment

Install exact tag `v1.16.7` through HACS and validate Home Assistant
configuration before restart. An active-clean restart is permitted only with
explicit user authorization; otherwise wait for positive docked,
non-servicing states from both vacuums. After restart, wait for the integration
to report loaded and for startup settling to finish, verify HACS reports
`v1.16.7`, and confirm active robot state was recovered from observation. If a
durable hold remains, use only the non-dispatching recheck flow after the robot
is positively error-free. Do not dispatch a clean solely for verification.
