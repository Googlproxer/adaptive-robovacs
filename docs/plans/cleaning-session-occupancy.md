# Cleaning session occupancy plan

## Purpose and baseline

Occupancy generated by a physical clean should not shorten a valid vacancy
window or train the scheduler to expect human arrivals. Ignore new detections
in the rooms being cleaned until the robot actually docks, then resume occupancy
tracking from docking. Give the registry-assigned dock room an additional short
cooldown.

Investigated on 2026-11-09 against `ae9c44f`, version 1.21.1 and Store schema 22.
Implemented on 2026-11-09 for v1.22.0, with Store schema 23. See the
[release notes](../releases/v1.22.0.md) for final validation and deployment steps.

## Baseline behavior and gaps

- [attribute_occupancy](../../custom_components/adaptive_robovacs/models.py)
  already applies during cleaning and returning. An onset can be attributed to
  a fresh matching robot visit; it preserves the earlier vacancy anchor and
  produces no vacancy-training sample. An established human episode stays
  blocking until clear.
- Matching allows 120 seconds around an onset. A visit expires after 180 seconds
  without fresh evidence, or after a bounded departure tail. Long occupancy can
  therefore become uncertain before the robot docks and lose its vacancy anchor.
- [The location adapter](../../custom_components/adaptive_robovacs/adapters/location.py)
  only supports a compatible native location contract and saved numeric area
  mappings. Other robots' known scheduler jobs do not provide attribution today.
- [The presence tracker](../../custom_components/adaptive_robovacs/robot_presence.py)
  opens visits only for moving robots. A direct dock observation closes the
  previous visit but does not open a dock-room visit or start a dedicated
  cooldown. A preceding observed dock-room visit can provide the ordinary tail,
  but that is not guaranteed.
- An expired robot episode becomes uncertain and remains so until the sensor
  clears. There is no docking boundary that splits a continuously occupied
  signal into ignored cleaning time and valid occupancy after docking.

The existing three-minute dispatch-ready confirmation is a robot readiness
gate. It does not implement dock-room occupancy cooldown or repair learning.

## Implemented behavior

### Limit suppression to rooms with cleaning evidence

Track one physical cleaning session per stable robot registry identity. Begin
it when cleaning is actually observed. An accepted command, forecast end time,
reservation, queued room or next stage alone must not start suppression.

For integration-owned scheduled and dashboard-manual work, use the dispatched
job's area IDs once that job is observed cleaning. Include all areas of an
actual multi-area physical command, but exclude future reserved jobs and stages.
This supplies room identity even without a compatible native location source.

For external Home Assistant or vendor-app work, include areas positively observed
as being cleaned through a supported, fresh, registry-mapped location source.
Do not infer an external clean's room from the robot's assigned dock room or
guess every room on its floor. External work with no known room retains ordinary
occupancy handling. Existing bounded transit attribution remains available for
rooms the robot only crosses.

Retain each covered room until observed docking, including after the robot moves
on to another room or returns home. Keep the pre-clean vacancy anchor separately
from raw sensor state. New detections in that interval do not reset the anchor,
produce human-arrival samples or increment human-arrival diagnostics.

Human occupancy already established before the clean remains blocking. A clean
cannot retroactively authorize itself or erase that prior evidence. Raw sensor
states remain visible and unchanged in Home Assistant.

### Resume at docking and recheck the current sensor state

Use the robot's observed `docked` transition, independent of job deletion,
completion credit, error acknowledgement or dispatch readiness. For each covered
room, read the current selected occupancy sources at that boundary, even if no
sensor state-change event occurs.

| State at docking in a cleaned room | Result |
| --- | --- |
| Clear, with uninterrupted session and source evidence | Restore the earlier vacancy anchor; add no arrival sample for the clean. |
| Occupied | Begin a new blocking occupancy episode at docking. The original detection time during cleaning must not become a human arrival time. |
| Unavailable or unresolved | Censor continuity, discard the old anchor and require fresh observations. |

If the signal remains occupied after docking, it must stay blocking and a later
clear starts a new vacancy interval. Attribute the retained pre-clean vacancy
spell's end to docking only where continuity was valid; never end it at a
detection that occurred inside the suppressed interval. Commit at most one
completed vacancy sample per spell.

### Apply a three-minute cooldown to the dock room

Resolve the home room from `DiscoveredRobot.dock_area_id`, which already uses
the vacuum entity's explicit area assignment or its owning device's assignment.
Use a fixed 180-second policy, separate from dispatch readiness. No
new household mapping or duration setting is needed initially.

Start cooldown on a real return from a cleaning session. Merely discovering an
already-docked robot at startup, or receiving repeated docked heartbeats, must
not start or extend it. A direct return-to-dock observation works even when
native room updates skipped the home room.

New robot-related dock-room detections remain excluded until cooldown expiry.
Handle an onset just before docking through a bounded pending match using the
existing 120-second matching interval; established earlier human occupancy stays
blocking. At expiry, read the current sensors explicitly:

- If clear, preserve the valid pre-return vacancy anchor.
- If occupied, start valid blocking occupancy at expiry, without backdating it
  into the clean or cooldown.
- If unresolved, censor continuity and require fresh evidence.

Only the dock room receives this extra delay. Other cleaned rooms resume at
docking. Missing or invalid dock-area assignment disables only this extension.
If another robot still covers the same room, wait until all applicable cleaning
sessions and dock cooldowns have ended before resuming that room's tracking.
Never derive an arrival sample from an intermediate overlapping boundary.

### Preserve scheduling and recovery safety

Suppression is evidence about a sensor signal, not permission to dispatch.
Keep robot traffic, active physical work and dock cooldown as explicit room
blockers for new work. Preserve pre-existing human occupancy, unresolved-input
blocking, final dispatch revalidation, adjacency protection, Party Mode and
observe-only behavior. An already-running physical clean continues normally.

Apply the same boundary rules before another physical stage or reserved room
starts. At a real intermediate dock, recheck the cleaned room immediately and
the dock room at cooldown expiry. A subsequent observed clean starts another
session; a planned continuation does not extend the previous mask automatically.

Pauses, faults, unavailable robots, source changes and unsupported location
changes must not create an indefinitely clear room. Invalidate continuity where
physical or sensor evidence is lost, censor the learning interval and use
blocking raw or unresolved evidence. A retained session record alone cannot
authorize a new start. Keep interrupted-clean recovery and completion credit
independent from occupancy masking.

The requested policy accepts that a person entering and leaving a covered room
entirely during cleaning can be excluded along with robot detections. A signal
still occupied at the applicable end boundary immediately becomes blocking.

## Implementation steps

1. Add immutable cleaning-session and cooldown inputs and a pure boundary
   decision in `models.py`. Keep ordinary short transit attribution intact.
   Represent masking separately from confirmed human vacancy and dispatch gates.
2. Add a bounded checkpoint per robot in `state.py`: registry identity, observed
   session onset, covered area IDs, dock boundary, cooldown expiry and evidence
   validity. Room attribution retains vacancy anchors without duplicating them
   per robot. Schema 22 migrates to 23 while retaining Store envelope version 1.
   Persist meaningful transitions.
3. Feed observed job starts and robot state transitions through the existing FIFO
   command path in `application/core.py`, `application/events.py` and occupancy
   handling. Capture occupancy at event time before job reconciliation can remove
   a completed job. Cover supported and unsupported location adapters equally
   when a physical job supplies known areas.
4. Extend `application/occupancy.py` and `application/policy.py` to mask learning,
   handle docking boundaries, re-read unchanged sensors and arm one earliest
   deadline through the existing lifecycle timer. Apply scheduling and stage
   blockers in the existing shared policy and dispatch paths.
5. Preserve startup's conservative treatment of observation gaps. Restore only
   validated session identities and pending boundaries; never restore a vacancy
   anchor across downtime. If docking happened offline, start conservatively
   from fresh observations rather than inventing its time or a completed sample.
6. Retire older vacancy samples once for rooms newly brought under the wider
   cleaning-session policy: existing samples lack enough provenance to remove
   only clean-generated arrivals reliably. Preserve last-cleaned records,
   cadence, duration and battery learning, jobs and unaffected rooms. Document
   the learning fallback and migration behavior.
7. Extend projections and occupancy evidence with cleaning suppression, dock
   cooldown, responsible robots and the next resume time. Preserve public entity
   IDs, raw occupancy and existing diagnostics. Update both dashboard copies
   together if their rendering changes; keep them byte identical.

Keep processing bounded by discovered robots and covered rooms. Use state
transitions and deadlines, with no new map requests, recorder scans or periodic
polling. Unchanged heartbeats must not add evaluations, Store saves or entity
publications. Persist no native map details or household runtime data in the
repository.

## Acceptance and release validation

Add model, application, Store and lifecycle coverage for:

- A long occupied signal throughout a clean, stale map updates during a known
  physical job, room departure long before docking and direct docking without
  a preceding home-room location frame.
- Clear versus continuously occupied sensors at docking and cooldown expiry,
  with no intervening state-change event. Verify onset rebasing and exactly one
  eligible vacancy sample, or none where continuity was censored.
- The dock room also being a cleaned room, overlapping robots, repeated docked
  notifications, immediate new departures, intermediate docks, multiple passes
  and ordered physical stages.
- Robots with no location source but a known physical job; external cleans with
  and without resolvable rooms; future queued rooms remaining protected.
- Pre-existing human occupancy, unrelated rooms, genuine occupancy after the
  boundary, unavailable inputs, source replacement, remapping, pause/error,
  cancellation, robot removal, unload and restart during each phase.
- Identical eligibility in previews and final dispatch, preserved adjacency and
  mode gates, and no added heartbeat evaluations or persistence writes.

Before implementation is committed, check live Core and available stable updates
and refresh compatible dependency and CI pins as required by `AGENTS.md`. Restore
the complete pinned test environment, then run the full unit, compilation,
coverage, lint, typing, relevant frontend and parity checks. An integration
release needs matching semantic versions, an annotated tag, a full GitHub
Release and passing CI. Deployment follows the repository's HACS and restart
procedure when deployment is requested.

Planning validation: all 125 tests in `tests.test_models` passed, including ten
existing robot-attribution decisions. Direct pure-model probes reproduced the
fresh-location exemption, expiry during a clean, early release after departure
and missing dock-arrival cooldown. The pinned native dependencies were restored
for implementation validation. Final results are recorded in the
[release notes](../releases/v1.22.0.md).
